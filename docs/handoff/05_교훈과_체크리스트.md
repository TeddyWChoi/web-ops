# 05. 교훈과 체크리스트

## 스포2에서 배운 것

### 역할
- **PM 직함과 실제 PM 역할이 다를 수 있다.** 누가 회의를 소집하고, 누가 일정을 쥐고, 누가 결정하는지를 직함이 아니라 실제 하는 일로 적어야 한다.
- **소통 창구는 하나여야 한다.** 요청자, 협의자, 검수자가 따로 있으면 디자인팀이 같은 결과물에 대해 세 번 의견을 받는다. 창구 한 명이 사업팀 의견을 모아 한 번에 전달하게 한다.
- **결정권자와 진행자를 나눈다.** 결정권자에게 모든 진행까지 몰리면 그 사람이 바쁠 때 전체가 멈춘다. 진행은 PM, 최종 결정은 결정권자, PM 선에서 안 풀리면 결정권자에게 올리는 경로를 적는다.
- **지원 인력은 그리는 일과 확인하는 일에 둔다.** 구조를 설계하는 일(웹기획)은 기획 담당이 하고, 지원 인력은 정해진 범위의 와이어프레임이나 체크리스트 기반 QA를 맡긴다.
- **팀장들이 PMO 역할을 나눠 맡는다.** 회사에 PMO가 없으면 PM이 놓친 것을 아무도 짚어주지 않는다.

### 일정
- **"○일까지 확인 가능한 사이트"는 기준이 아니다.** 그날 무엇이 완성돼야 하는지 화면 단위로 적는다. (스포2: 카드사 심사용으로 홈·결제 화면만 먼저, 나머지는 "준비중")
- **수정 마감일과 QA 기간을 처음부터 잡는다.** 없으면 오픈 직전까지 수정 요청이 들어온다. 화면이 나오는 날부터 1차 QA, 수정 마감 후 2차 QA.
- **한 사람에게 작업이 몰리는지 본다.** 스포2는 개발 담당이 바뀌면서 홈페이지·사전예약·플랫폼 연동이 한 명에게 몰렸다.
- **일정 변경은 지연이 생긴 팀의 팀장이 보고하고 결정권자가 확정한다.** 실무자끼리 합의한 변경은 효력이 없다고 적어둔다.
- **약관·개인정보·콘텐츠처럼 개발이 아닌 일도 일정에 넣는다.** 빠지기 쉽고, 오픈을 막는다.

### 문서
- 결정이 바뀐 날짜를 남기면 나중에 "왜 이렇게 됐지"를 설명할 수 있다.
- 사람 평가가 들어간 문서는 공유할 수 없게 된다. 구조와 사례로만 적는다.
- 녹음 텍스트는 이름과 용어가 깨진다. 확실하지 않으면 확인 필요로 둔다.

## 새 프로젝트를 등록할 때 체크리스트

**사람과 창구**
- [ ] 결정권자는 누구인가
- [ ] PM(진행·소통 창구)은 누구인가
- [ ] PM 선에서 안 풀릴 때 누구에게 올리는가
- [ ] 결정권자 부재 시 대리는 누구인가
- [ ] 웹기획, 디자인, 웹 개발, 검수 담당은 누구인가
- [ ] 인프라, 클라이언트 등 웹과 맞물리는 팀의 담당은 누구인가

**작업 범위**
- [ ] 기존 구조 수정인가, 신규 기능이 들어가는가
- [ ] 개인정보를 수집하는가 (수집하면 약관·동의·보관 기간·검토 담당 필요)
- [ ] 결제가 있는가 (있으면 PG·카드사 심사 일정과 심사 필수 화면)
- [ ] 연령 제한, 확률 공개 등 법적·권고 사항이 있는가
- [ ] 오픈 전에 채울 콘텐츠(공지, 게임 소개, 이벤트 등)와 담당은

**일정**
- [ ] 오픈일과 그 근거
- [ ] 오픈을 좌우하는 외부 일정 (심사, 통신사 회신, 등급 등)
- [ ] 화면별 완성일
- [ ] 수정 마감일, 1차·2차 QA 기간, 최종 확인일
- [ ] 같은 기간 같은 사람에게 겹치는 다른 프로젝트가 있는가

**운영**
- [ ] 정기 회의 일시, 소집·진행 담당, 참석자
- [ ] 회의 내용 정리·공유 담당
- [ ] 요청은 어디로 (지라), 팀 간 소통은 어디로 (팀즈), 전원 공유는 어디로 (공통 채널)
- [ ] 페이지 공유 범위
